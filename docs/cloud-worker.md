# The cloud worker

Heavy jobs run on a GPU rented from Vast.ai. The worker keeps nothing that matters (see `design/local-cloud-split.md`); home remembers only which instance is ours, in `~/.local/state/vi/cloud.json`.

## Commands
- `vi cloud offers`: the ten cheapest machines that fit the config. Read only.
- `vi cloud up --cap USD --until TIME [--offer ID] [--yes]`: shows the cheapest offer, its worst case next to your cap, and your credit, asks, then rents it and waits until ssh answers. `--cap` is the most the rental may cost and `--until` when that approval expires (an RFC 3339 timestamp, or `HH:MM` meaning today). It refuses before renting anything if the deadline has passed, the worst case (`max_hours` at this price) would exceed the cap, or the account holds less than the cap. It rents at most one offer: if that machine fails to boot it's given back and `up` exits nonzero rather than renting a replacement. Run it again while a worker is up and it just reuses it (the flags are still required).
- `vi cloud down`: destroys our worker, plus any instance labelled `vi-worker` that home lost track of. It never touches other instances on the account. It prints the credit before, after, and the difference, so you can see what the rental actually cost.
- `vi cloud status`: state, price, time up, rough spend so far, idle minutes left, credit, and any other instances on the account (a stopped instance still bills for its disk).
- `vi cloud reap`: releases the worker if it has been idle for `idle_minutes` or up for `max_hours`. Before an idle release it asks the worker over ssh whether an interactive session or another ssh connection is using it (`who`, plus `ss` for established inbound ssh connections), and keeps the worker when the answer is yes or when the check can't run; the `max_hours` limit releases it regardless.
- `vi cloud ssh [command]`: a shell on the worker.
- `jobs/check-worker.sh`: checks the full round trip a GPU stage makes. It sends a random token up through `on-worker.sh` as a stage input, runs a tiny job that copies it into its output and its checkpoint, and passes only if both copies come home matching. It prints what the worker has (GPU, disk free, Python, torch). Run it after `vi cloud up` to confirm home can reach the worker, send files, run code, and receive worker-pushed results and checkpoints. Home creates a reverse SSH tunnel and a restricted, temporary rsync receiver; no home credentials or agent are stored on the worker.
- `vi cloud env` and `vi cloud touch`: used by `jobs/on-worker.sh`.
- `python3 jobs/progress.py corpus/tali [--watch 60]`: how far a running stage has got, as a percentage per pass, read from its log at home; `--watch` adds the time left in the current pass. It reads only logs, so it works for GPU and home stages alike and changes no stage's key.

## Keeping the budget safe
Three guards, so a forgotten worker can't drain the credit:
1. **On the worker.** `jobs/worker-onstart.sh` runs at boot and starts a watchdog, checked once a minute. This works while the home machine is asleep or gone for good. It releases the instance in four cases:
   - **Idle.** After `idle_minutes` with no running job and no ssh session that runs a command. Home's reverse tunnel (`ssh -N`) runs no command, so it does not keep the worker alive; a stage, a poll or an interactive login does.
   - **Pending hold.** When a finished job still has un-acked checkpoint epochs in `pending/`, the watchdog waits for them for `PENDING_HOLD` minutes after the job's `rc` file (default 120), but never more than 30 minutes, then releases.
   - **`max_hours`** after the first boot, whatever it is doing. If checkpoint epochs are still pending, this release stops rather than destroys, so the un-pushed work keeps its disk.
   - **The hard cap**, `max_hours` + 10 minutes after the first boot. It always destroys, even with ssh sessions open, pending work, or a restart after a stop.

   Every release first tries to destroy (DELETE with the instance's own `CONTAINER_API_KEY`, up to three tries 30 s apart). If Vast refuses or the call fails, it falls back to stopping the instance (decision D4), with the same key and route: a PUT of `{"state":"stopped"}`, the REST form of the documented `vastai stop instance $CONTAINER_ID`. A stop ends the GPU charge but still bills disk until `vi cloud down`, the dead-man timer or the next `vi cloud up` destroys it. The pending-hold and `max_hours`-with-pending releases try the stop first and fall back to DELETE. `/var/log/vi-watchdog.log` records which path ran: `release: <reason>`, then `destroyed`, or `destroy-failed` (with curl's error, such as the HTTP 403) followed by `DELETE refused; fallback stop` and `stopped; storage bills until home destroys`. Ssh sessions do not see the container's environment, so the boot script saves the `CONTAINER_*` variables to `/root/.vi-env` (mode 600). A watchdog that `on-worker.sh` restarts over ssh reads that file and defaults its job root to `/root/vi-jobs`.
2. **At home.** `vi cloud reap` applies the same limits from home's own clock. Its idle release first checks the worker over ssh for an interactive session (`who`) or another established ssh connection (`ss`); only a worker it can see is idle is released, and `max_hours` still releases regardless. Run it from a timer:

   ```nix
   systemd.user.services.vi-cloud-reap.script = "vi cloud reap";
   systemd.user.timers.vi-cloud-reap = {
     wantedBy = [ "timers.target" ];
     timerConfig.OnCalendar = "*:0/5";
   };
   ```

3. **The dead-man timer at home.** Every `vi cloud up` that rents arms a transient systemd user timer, `vi-deadman-<id>`, at the rental's hard cap: the earliest of `--until`, `max_hours` after the start, and the point where `--cap` would be spent at this price. So `--until` now also ends the rental at that time. When it fires it runs `vi cloud deadman fire <id>`, which destroys that instance and checks it is gone. It is cancelled only by a verified destroy (`vi cloud down --verify`, or the timer itself); a plain `vi cloud down` leaves it armed, and when it later fires it finds the instance gone and cancels itself. If the user manager isn't reachable `up` refuses before renting, and if arming fails after the create, `up` destroys the new instance. `jobs/paid_run.py` keeps moving the timer to 30 minutes from now while the run is healthy (`vi cloud deadman extend <id> --grace SECS`, never past the cap), so a crashed or hung run is cleaned up within about half an hour. `vi cloud deadman show <id>` prints the stored fire time and cap. The timer is transient and does not survive a home reboot; the worker watchdog covers that case.

The worker-side watchdog hasn't run on a real instance yet. **Open item:** Vast does not document whether the instance key may DELETE (destroy) its own instance; it documents only the self-stop. Proving DELETE on a real worker is left to the next approved debug pass. Until then the stop fallback limits the cost, and the home layers still destroy. On that pass, after the idle timeout on a short `idle_minutes`, run `vi cloud ssh cat /var/log/vi-watchdog.log` (or read Vast's instance list) to see whether `destroyed` or the stop fallback ran.

The watchdog spots home's tunnel because the tunnel's sshd session process has no child process. That holds for the `sshd: root@notty` and `sshd-session: root@notty` process names, and it is tested with a fake `pgrep` only. The `on-worker.sh` reattach check uses the same rule: a pending-only job is live for up to `VI_PENDING_HOLD` minutes, capped at 30, matching the watchdog.

## Config
`~/.config/vi/cloud.toml` (or `$VI_CLOUD_CONFIG`). Every field is optional; these are the defaults:

```toml
image = "pytorch/pytorch:2.8.0-cuda12.8-cudnn9-runtime"
disk_gb = 60
idle_minutes = 20
max_hours = 4          # 0 = no limit
boot_minutes = 15      # give up on a machine that hasn't answered ssh by then
label = "vi-worker"

[search]
gpu_names = []         # e.g. ["RTX 3090", "RTX 4090"]; empty = any
min_gpu_ram_gb = 24
max_dph = 0.40         # dollars per hour
min_reliability = 0.98
min_inet_down_mbps = 200
min_cuda = 13.0
min_compute_cap = 800  # Ampere or newer, for bf16 and flash attention
verified = true
countries = []         # e.g. ["US", "CA"]; empty = anywhere
exclude_countries = ["CN"]   # never rented from; [] allows every country
```

`countries` takes two-letter codes (Vast.ai's geolocation). A nearer worker uploads a little faster: one rsync stream slows down as the round trip grows.

`exclude_countries` (default `["CN"]`) is sent to Vast as `geolocation notin [...]`, and `vi cloud up --offer` refuses an offer whose geolocation ends in an excluded code. If `countries` is also set, an excluded code is dropped from it.

**What an hour costs (checked 2026-11-26).** The search's `dph_total` is priced with the storage the query asks for (`allocated_storage`, 8 GB when omitted), so with a 125 GB disk it understated the real rate: an offer listed at $0.17/hr can bill $0.31/hr. The query now sends `allocated_storage = disk_gb`, and `vi` prints and caps on the billed rate `dph_base + storage_cost x disk_gb / 730` (never below the listed `dph_total`; 730 h per month is this repo's assumption, Vast gives no month length). `max_dph` is judged on that full rate. Bandwidth is billed per GB moved (`inet_up_cost`, `inet_down_cost`, $/GB), so it is not in the hourly rate; `vi cloud up` prints the two prices next to the worst case. Unverified: whether Vast's `dph_total` is exactly `dph_base` plus storage (the docs list the fields, not the sum), which is why the rebuilt figure is only ever allowed to raise the rate. Sources: https://docs.vast.ai/api-reference/search/search-offers (fields, `allocated_storage`, geolocation `notin`), https://docs.vast.ai/documentation/instances/pricing (compute, storage and bandwidth components), `vastai search offers --explain --api-key dummy` (its `--storage` default of 5 GiB is sent as `allocated_storage`). The plan's "disk on top" line below stays as an extra margin and now double counts the disk against `max_dph`.

`min_cuda` must cover the CUDA that the jobs' torch was built for. textscore's vLLM brings torch built for CUDA 13, hence the 13.0 default; on an older driver torch sees no GPU, and textscore stops at once rather than crawl on the CPU. Jobs built for CUDA 12 run on these newer drivers too. The boot script also installs gcc, which Triton (inside vLLM) needs at run time; `check-worker.sh` reports whether it's there. For textscore's FP8 LLMs, prefer GPUs with native FP8 (Ada or newer: `"L40S"`, `"RTX 6000Ada"`, `"RTX PRO 5000"`); on Ampere cards such as the A6000, vLLM has to compile a fallback kernel first.

The API key comes from `$VAST_API_KEY` or `~/.config/vastai/vast_api_key` (where the `vastai` CLI saves it). Your ssh public key must be on your Vast account (Account, SSH keys); new instances get it automatically.

## Running a dataset stage on the worker
Prefix the stage's command with `jobs/on-worker.sh`:

```toml
[stage.label]
command = ["../../jobs/on-worker.sh", "--put", "states.toml", "python3", "jobs/label.py"]
inputs = ["clean"]
files = ["../../jobs/label.py", "states.toml"]
```

It rsyncs `jobs/`, the settings, each input folder and the `--put` files into a fresh folder on the worker, runs the command there with the usual `VI_*` variables pointing at the copies (`--put` files land in `files/`), and the worker pushes `VI_OUT` home. It deletes the folder on the worker whether the job worked or not. Game audio only ever travels between home and the worker over the direct SSH connection and its reverse tunnel, and doesn't outlive the job there. Destroying the instance wipes its disk too.

**Worker-initiated returns.** Before any inputs or paid job run, `on-worker.sh` starts `jobs/worker-return.sh` on home, which launches a temporary rsync daemon bound to `127.0.0.1`. Home then opens a second SSH connection with `ExitOnForwardFailure=yes` and a reverse forward whose worker listener is also bound to `127.0.0.1`. The worker must push a random token through that tunnel and home must read the exact token back; otherwise the stage stops before training. The worker pushes checkpoints every `VI_SYNC_SECONDS` and final output at the end. Home does not pull them.

The receiver has separate `vi-out`, `vi-checkpoint`, and `vi-publish` modules rooted at their exact destination folders; `vi-publish` is the durable per-attempt checkpoint dir where finished epochs land to be verified. All three are write-only, refuse deletion, allow only localhost, are hidden from module listings, and limit connections to one. `use chroot = false` keeps the daemon unprivileged; `munge symlinks = true` prevents an uploaded symlink from escaping the destination. No `auth users` or secrets file is used: the loopback-only SSH tunnel provides encryption and access control, and both receiver and tunnel close when the stage ends. No home SSH login, private key, or forwarded agent is available to the worker. `VI_RETURN_PORT` can override the automatically selected loopback port. Jobs can push additional files with `VI_RETURN_PORT=... jobs/worker-return.sh push SOURCE vi-out` (or `vi-checkpoint`, `vi-publish`).

`VI_WORKER_HOST=local` uses the same worker-push path without SSH, which lets CI exercise the receiver, output/checkpoint transfer, and failure handling. `jobs/test_worker_return.py` also starts a disposable OpenSSH server to test a real reverse tunnel.

**Uploads.** Home's disk is the slow end: the corpus sits on spinning, encrypted disks that other services also use, and reading a stage's thousands of small audio files ran at about 0.7 MB/s on 2026-10-17, against about 2.2 MB/s of uplink. So `on-worker.sh` does three things before the upload:
- **Packs first.** Each input over `VI_PACK_MIN_KB` (default 1024) becomes one zstd'd tar, before the worker is even looked up, so the slow reading happens while nothing is billed. Bundles are kept in `VI_BUNDLE_DIR` (default `~/.cache/vi/bundles`, at most `VI_BUNDLE_CACHE_MB`, default 4000, least recently used dropped first), keyed by the folder's path and file listing, so a rerun or a second stage with the same input reuses them. Each is uploaded as one file and unpacked on the worker (or streamed and unpacked there if the worker has no zstd). zstd saves only about 13% on her WAVs; FLAC would save about 36% but needs `flac` on both ends, so it isn't used yet.
- **Can wait for the worker.** `VI_WAIT_FOR_WORKER=MINUTES` makes it wait that long for `vi cloud up` instead of failing, so you can start `vi dataset run`, let it pack, and rent when it says it's waiting. Without it, a run with no worker packs, keeps the bundles and stops; the run after `vi cloud up` starts straight at the upload.
- **Checks the uplink.** A timed 8 MB upload estimates how long the inputs will take; if that's over `VI_MAX_UPLOAD_MINUTES` (default 30) it stops before sending anything, unless `VI_UPLOAD_ANYWAY=1`. It logs `upload: <inputs done>/<inputs>`, which `jobs/progress.py` shows.

**If the worker dies part way.** Jobs save each clip's results in `VI_CHECKPOINT` as they go, and the worker pushes that folder home every `VI_SYNC_SECONDS` (default 60) and once more when the job ends, however it ends. If the instance is lost, the watchdog or `max_hours` ends it, or the credit runs out, the stage fails with its checkpoint at home in `stages/<stage>/.checkpoint-<key>/`. Run `vi cloud up` and `vi dataset run` again: the checkpoint goes up to the new worker and the job skips clips already done. At most about a minute of work is lost. Editing the job's code or settings in between starts the stage over.

For tests, `VI_WORKER_HOST=local` with `VI_WORKER_ROOT=<folder>` runs the "worker" in a local folder; `crates/vi/tests/on_worker.rs` does this, so CI needs no GPU or rented machine.

## One command for the paid OmniVoice fine-tune
`jobs/paid_run.py` runs the whole paid flow unattended, driving the `vi` binary (`$VI_BIN`; if unset, `<repo>/target/release/vi` when that executable exists; otherwise `vi` on PATH). It rents the cheapest offer that has not failed yet, runs the `omnivoice_preflight` stage (tunnel, receiver, token push, worker gates), then `omnivoice_train`, checks what came home, and releases the worker. Start it only with Brandon's approval of the cap and hours for that run. The code lives in the `jobs/paidrun/` package; `jobs/paid_run.py` is the entry point and keeps every old name importable.

```sh
python3 -I jobs/paid_run.py --run-id omnivoice-ft-1 --cap 5.00 --max-hours 8 \
    --config jobs/paid-run/omnivoice-run-cloud.toml [--countries "US,DE" | --countries eu] [--max-attempts 3]
```

- In the full run, `--cap` and `--max-hours` cover all attempts together (the debug pass gives each rental its own hours; see below). Each attempt gets the remaining cap on `vi cloud up --cap` and a config copy whose `max_hours` is the hours left.
- Only a failed cheap worker gate is retried (stderr contains `worker-preflight: ...` for disk, RAM, CUDA version, VRAM, cores or a missing tool, or `worker upload ETA` for an upload line too slow for `max_upload_minutes`); the `worker-preflight: ok` line does not count: the worker is released, that offer and any relisting of the same machine (same GPU, place, cores, RAM and uplink; `vi cloud offers` does not print machine ids) is excluded, and the next cheapest is rented, up to `--max-attempts`. Any other failure releases the worker and stops.
- `--plan` prints the effective plan and exits without calling `vi`.
- State is kept in `~/.local/state/vi/paid-run/<run-id>.json` (`$VI_PAID_RUN_STATE_DIR` overrides). A killed run is started again with the same `--run-id` and the same limits: a worker still up whose train stage had started is adopted (the stage reattaches); any other leftover worker is destroyed first, so a second rental is never made on top of a billing one.
- Run files, in `~/.local/state/vi/paid-run/<run-id>/` (next to the state file):
  - `run.log` is a copy of everything the run printed, with a `===== attempt N of M ... =====` header per attempt and one for the train stage. It is capped at 200 MB.
  - `diag-attempt-<n>-<outcome>.txt` is written just before a FAILED worker is destroyed: the raw `nvidia-smi` output, `pip freeze` of the worker's venvs and the tail of its job logs. It is best effort, cut off after 25 s (`PAID_RUN_DIAG_SECONDS` changes this) and limited to 256 KiB, and a hung or failed fetch never delays the destroy. A successful attempt writes none.
  - `stage-tail.log` is the last lines of the stage output the run is watching, in the preflight as well as the train stage; `paid_run.py status` reads it.
- `--plan` (and the pre-rent checks) also verify the built `omnivoice_data` folder's clip ids (no `.`, unique, style ids are dev ids; exit 12 if not) and list unverified markers whose checkpoint folder is empty or missing, with the `checkpoints.py abandon` command to run by hand. Nothing is deleted.
- SIGINT and SIGTERM stop the child stage and release the worker (`down`, then `down --force` if it refuses).
- Exit codes: 0 done, 2 bad arguments, 3 `up` failed, 4 preflight failure that is not a retryable gate, 5 a cheap worker gate failed on all attempts, 6 train failed, 7 home results did not verify, 8 interrupted, 9 worker could not be released (check `vi cloud status`), 10 no offer or budget left, 11 the config's `disk_gb` is too small for the worker's free-disk gate, or home is short of the stage's `min_home_gb` plus reserve, 12 a clip id in the built data folder would break tokenising (dotted, repeated), 13 the home real-path check failed or could not run (see below), 14 the pinned base-model revision is gone, resolves to another commit or has other file sizes on Hugging Face, or could not be checked (3 tries, 60 s each) and is not in the home cache, or the check's own code fails (nothing rented; the check uses only the Python standard library, since the paid-run card starts the system `python3 -I`), 15 the home Vast-limits rehearsal has no valid pass record for this HEAD (run `jobs/rehearsal/vast-limits.sh --expect green` on a clean tree; see `jobs/rehearsal/README.md`; nothing rented), 1 unexpected.
- Disk check (before any offer is listed): the worker preflight refuses less than `VI_MIN_DISK_GB` GiB free (default 100, read from `jobs/voicetune-fresh.sh`). A 100 GB rented disk showed 95 GB free, so `paid_run.py` requires `disk_gb - 5 >= gate`, prints the result in the plan (`--plan` exits 11 on FAIL, 0 on OK) and exits 11 with nothing rented otherwise. A config with no `disk_gb` counts as Vast's default 60. `omnivoice-run-cloud.toml` uses 125.
- After training it checks that home holds checkpoints 1000, 2500, 4500 and 5000 with `VERIFIED` and no unverified marker, and that `step-1000`, `step-2500` and `step-5000` listening sets (with `listening.jsonl` and `README.txt`) are in the stage's `platter` (`--platter`, default `corpus/tali/stages/omnivoice_train/current/out/platter`). Human listening decides voice quality. For each set it also writes `step-N/clips.toml` (one clip per `listening.jsonl` row, audio at `step-N/wav/<label>.wav`, unblinded, answers her / partly / not her). The review hub (`vi review corpus/tali`, port 8737) already finds any `clips.toml` under a stage's current output, so the three sets then show up there as clip lists; a single model has nothing to blind against, so there is no A/B. If a row has no wav at home, the run exits 7. This needs the default `--platter` (or any folder under that stage's current output); the hub display itself has not been checked on the real service.
- Worker gates run in `jobs/worker-preflight.sh` before the push test and before any upload: `min_disk_gb` (GiB, 100), `min_ram_gb` (GiB, 28: the 30 GB offer filter is 30000 MB = 28.6 GiB), `min_cuda_version` (12.8, compared part by part; it already implies the driver, so no driver number is hard-coded), `min_cpu_cores` (4) and `min_vram_gb`, all in the stage settings. The offer filter's `min_gpu_ram_gb = 24.1` is MB x 1000 in Vast's REST API (docs.vast.ai search-offers, checked 2026-11-18), so every offer it passes also reads at least 23.5 GiB live. The push rate is a warning, never a gate (round 19, 2026-11-23): the preflight prints the measured MB/s and the time one full checkpoint (`checkpoint_bytes`) takes at that rate against `max_upload_minutes` and the hours left, and prints `worker-preflight WARNING: slow push` below `warn_push_mb_s` (2.5); it never refuses or retries a worker.
- Home checks before renting (`--plan` too): home disk against each stage's `min_home_gb` and `home_gate_reserve_gb` (same `checkpoints.py gate` as `on-worker.sh`; exit 11 when short), the bundle cache (the same key `on-worker.sh` computes, read-only: `built and current (<key>)`, or `not built, will pack before renting`, which costs home CPU and disk only; a cold pack would otherwise happen while the worker bills), a disk-billing line (Vast bills disk on top of the GPU price per GB-hour until the instance is destroyed; the plan bounds it at an assumed $1.00/GB/month, `disk_gb x 1.00 / 730 x hours`, so 125 GB for 8 h is about $1.37; an estimate, since the real `storage_cost` is only known from the live offer), and the pinned base-model revision. `--plan` makes no network call for it: it runs the whole revision check on canned Hub replies (`hf check code` line; exit 14 if even that fails, for example a missing module), and a real run then asks the Hub before renting.
- Home real-path check (`--plan` too; exit 13 with nothing rented if it fails or cannot run): `jobs/omnivoice-ft/home_realpath_check.py` runs the worker's real data path on CPU for 8 train, 2 dev and 2 replay-stand-in clips (real train clips; the check never uses mood labels). It tokenises them with upstream `extract_audio_tokens`, calls `StyleShardProcessor` directly on raw samples (so errors are not swallowed by the stream dataset), runs `train_ft._build_data` and pulls collated batches from the real loader. omnivoice-ft-r6 failed on a rented GPU on a bug this finds. It needs a throwaway CPU venv, which it never builds on its own: if `~/.cache/vi/home-cpu-venv-<hash>` is missing, the plan prints the one `uv` command to build it (about 430 MB of downloads; pins in `jobs/requirements-omnivoice-home-cpu.txt`, identical to the worker pins except the CPU torch wheels) and exits 13. It also needs the pinned base-model snapshot in `~/.cache/huggingface` (or `VI_BASE_MODEL`), and 4 GB of free RAM. It runs under `nice -n 19`; a pass is cached in `~/.cache/vi/realpath-check/<code hash>.json`, keyed on `ft_data.py`, `train_ft.py`, `omnistyle/*.py`, the check itself, the requirements and the data folder id, so only a code or data change reruns it (about 4 minutes on CPU, almost all of it tokenising). `--realpath-forward` adds one forward and backward step on the real model with the KL reference (no optimizer; about 1 minute, needs 12 GB of free RAM, otherwise the plan says it stopped at the collated batch). It proves our code works against the pinned omnivoice, transformers and torch on real tokenised clips. It does not prove anything about CUDA, bf16, GPU memory at the default batch (2048 tokens x 4 accumulation since round 25), DDP, throughput, GPU replay generation, checkpoint saving, the network, or how the voice sounds. The audio is read in place and tokenised into scratch under `~/.cache`; nothing is uploaded or copied into the repo.
- Rehearsal gate (`--plan` shows it without failing; a real run exits 15 with nothing rented): before any `vi` or Vast call, `paid_run.py` needs `~/.local/state/vi/rehearsal/<HEAD sha>.pass`, the record `jobs/rehearsal/vast-limits.sh --expect green` writes after a PASS with its default limits on a clean tracked tree. The record must be valid JSON naming that HEAD and its tree. A new commit therefore needs a new green run (about a minute on home CPU). There is no bypass, not even on resume; `VI_REHEARSAL_STATE_DIR` only moves the folder for tests. If a resumed run's state file still has an open attempt, the exit-15 message says that worker may still be up and keeps billing until brought down, and gives the command to do it (`vi cloud down --force`, then `vi cloud status`). Details in `jobs/rehearsal/README.md`.
- Driver decision (no code): CUDA 12.8 needs NVIDIA driver >= 570.26 (GA) per the CUDA toolkit release notes, Table 4 (docs.nvidia.com/cuda/cuda-toolkit-release-notes, checked 2026-11-18).
- The existing `min_cuda_version = 12.8` check in `worker-preflight.sh` (reads the `nvidia-smi` `CUDA Version` header) and the `cuda_max_good >= 12.8` offer filter already enforce that, so no separate driver-number gate was added.
- CUDA 12.8 Update 1 would need 570.124.06; that is not enforced.
- The worker requirements are pinned (`jobs/requirements-omnivoice-worker.txt`, resolved with `uv pip compile` for Python 3.11, which is what the image's conda ships per the pytorch v2.8.0 Dockerfile, `ARG PYTHON_VERSION=3.11`). torch and torchaudio 2.8.0 are listed but come from the image (`2.8.0+cu128` satisfies `==2.8.0`).
- Tests: `jobs/test_paid_run.py` (stub `vi`, no Vast, no network).

### Debug pass (`--debug-pass`)

A debug pass rents one worker (two at most, see "Host drop" below) and tries every step of the real flow on a small slice, in 12 separately timed stages, so a single short rental shows every problem at once instead of one per paid run. Unlike a real run it never stops at the first failure. Each stage prints `PASS`, `FAIL` (with the last lines of its log), `SKIP-dependent` (naming the earlier stage it needs) or `SKIP-no-time` (not started because the rental's time ran out; shown apart from FAIL in the summary), and stage 12 always destroys the worker, even after a failure, a timeout or an exception.

| Stage | What it proves |
| --- | --- |
| 1 host-cuda | `nvidia-smi` runs, the CUDA version and VRAM meet the stage's floors |
| 2 disk-limits | free disk, `ulimit -n` (nofile), `/dev/shm`, cores and RAM |
| 3 upload | the reverse tunnel, receiver and random-token push, then the slice upload |
| 4 venv | the pinned venv builds; the key imports, `python -m accelerate.commands.launch` and the tokeniser entry point work |
| 5 base-model | the pinned Base revision downloads and its size table matches |
| 6 tokenise | the slice tokenises and passes the count guard |
| 7 cuda-load | the CUDA gate, then the replay set generated on the GPU |
| 8 train-steps | a few real train steps through accelerate, with the KL reference, at the real run's batch (the trainer's defaults: 2048 tokens x 4 accumulation), and the peak GPU memory |
| 9 ckpt-push | checkpoint-5 is saved, pushed home and verified at home |
| 10 listening | a small listening set from checkpoint-5 comes home |
| 11 resume | training resumes from checkpoint-5 |
| 12 down | the worker is destroyed |

```sh
python3 -I jobs/paid_run.py --debug-pass --run-id omnivoice-debug-1 --cap 1.00 --max-hours 1.25 \
    --config jobs/paid-run/omnivoice-run-cloud.toml [--debug-rows 128] [--countries eu]
```

- **Approval.** A debug pass is a paid rental, so it needs Brandon's explicit approval of that run's cap and hours, given exactly like a real run (a one-click `paseo send` card to the agent that runs it). Approval for one pass does not cover a second, and a failed pass is never retried on another offer, except for the single host-drop re-rental below, which stays inside the same approved cap and gets its own `--max-hours`.
- **Hours and cost (round 21).** In the debug pass `--max-hours` is per rental (1.25 h is the agreed value; paid_run does not enforce that number), and `--cap` is shared by both rentals. `--plan` prints the worst case without calling anything: `worst case = min(cap, 2 x max_hours x max_dph) + disk_gb x 1.00 / 730 x 2 x max_hours`, where `max_dph` is the config's price ceiling. An offer is rented only if its `$/hr x max_hours` fits the cap left, and disk is billed on top (assumed $1.00/GB/month). With `--cap 1.75 --max-hours 1.25`, `max_dph = 0.60` (the shared config since round 27) and 125 GB, that is GPU $1.50 (inside the $1.75 cap) plus disk $0.43, $1.93 in all. (Up to round 26 the ceiling was 0.31: `--cap 1.00` gave GPU $0.78 plus disk $0.43, $1.20.) A typical pass should finish in under 30 minutes, so it costs about half the offer's hourly price.
- **Time per stage.** paid_run passes the rental's hours left to the worker (`VI_HOURS_LEFT`, less the time `on-worker.sh` already spent on the preflight and upload). Before each of stages 3 to 11, `jobs/debug-pass.sh` cuts the stage's limit to the time left minus a 15-minute margin (`VI_DEBUG_MARGIN_SECONDS`); when that is below the stage's minimum it prints `SKIP-no-time` and does not start it. Stage 9's limit is `1.5 x checkpoint-5 bytes / the push rate the preflight measured`, at least 600 s (600 s when no rate was measured). Stage 8 writes its trainer output to the stage log as it runs, so a stage cut off by its limit still shows how far it got. The worker gives up on an unreachable host after 5 minutes in the debug pass (`VI_LOST_MINUTES=5`; the full run keeps 30), and each return-path check while it waits is capped at 60 s, so that limit and the tunnel refresh keep running.
- **Why a stage failed (round 23).** A `FAIL` first lists `key:` lines picked out of the stage log wherever they are: the trainer's own `train_ft:` lines, exception lines, out-of-memory text, and accelerate's `returned non-zero exit status N` (shown as `accelerate: child returned non-zero exit status N`). Then come `last 12 lines:` and the log's tail. paid_run keeps the `key:` lines in the summary even past its 12-line cap. When stage 8's trainer fails, its `train.log`, and its `oom.json` if it wrote one, are copied to `debug/08-train.log` and `debug/08-oom.json`, which come home with the stage output. On an out-of-memory error the trainer prints torch's own first line, the GPU's free and total memory, and its peak reserved and peak allocated memory, and writes the same figures into `oom.json`.
- **Out of memory through accelerate (round 23).** accelerate turns the trainer's exit 76 (out of GPU memory) into exit 1. So `jobs/worker-job.sh`, and stage 8 of the debug pass, treat a failed attempt that wrote `oom.json` during that attempt as exit 76. The retry then halves `batch_tokens` and doubles gradient accumulation; at the floor (2048 tokens) the job exits 76. Since round 25 the default batch is already 2048 tokens x 4 accumulation, so a run on the defaults stops at its first out-of-memory failure instead of retrying smaller. An `oom.json` left over from an earlier attempt does not count. paid_run reads exit 76, or "GPU out of memory" in the output, as an out-of-memory failure.
- **Memory fix and diagnostics (round 25).** The default batch is 2048 tokens per micro-batch with 4-step gradient accumulation, so each optimizer step still sees 8192 tokens; both numbers live only in `jobs/omnivoice-ft/ft_guards.py`, and stage 8, the preflight probe and the real run all pass no batch flags, so they all run these defaults. The frozen KL reference is held in bf16 (its rotary buffers stay fp32); the KL itself is still computed in fp32, and the student is unchanged. The trainer prints `train_ft: vram peak: allocated X GiB reserved Y GiB` after the first optimizer step and at the end of training (only on CUDA), and one `train_ft: sdpa-mask-warning:` line saying whether the first training forward raised an attention-kernel warning; stage 8 repeats these lines after the trainer's log. They are diagnostics only: the VRAM gate still reads the older `train_ft: vram peak X of Y GiB` line. On an out-of-memory failure, `oom.json` keeps every traceback frame and a `where` field (`student forward`, `kl reference forward`, `backward`, `optimizer step`), and one `train_ft: oom in ...` line carries the same into the debug-pass excerpt.
- **KL reference on replay rows only (round 26).** The frozen KL reference's forward now runs only on the rows the KL term uses (the public replay rows with a masked position), not on the whole micro-batch; each row attends only to itself, so the KL value is the same. A micro-batch with no replay rows skips the reference entirely. The trainer prints `train_ft: kl-rows: used U of B rows (share S)` once per optimizer step that contains a logged micro-step, summed over that step's micro-batches, and stage 8 of the debug pass repeats these lines with the r25 diagnostics. Diagnostics only: no gate reads them.
- **Host drop.** If ssh loses the worker (ssh exit 255, "closed by remote host", a refused or reset connection) during a stage that printed no result, paid_run reads the instance status from Vast (`vastai show instance <id> --raw`) twice, at least 60 s apart. It is a confirmed host drop only when both reads say the instance is neither `running` nor `loading` (round 21; `loading` added in round 27). Since round 27 Vast no longer listing the instance also counts: `show instance` succeeds with `{"instances": null}` (or an empty list), or it answers without any status while `vastai logs` says "No such container" (what omnivoice-ft-dbg5 saw on 2026-11-24). That "gone" answer confirms a drop only if `vi cloud ssh true`, tried once more, is still refused or unreachable. If home's own Vast call fails or hangs, or either read says `running` or `loading`, or the instance is gone but ssh answers again, it is not a host drop. The stage then reads `HOST-DROP (status X)` instead of "never reported". Our own check failures (gates, preflight, nofile, push speed) never count as a host drop.
- **Vast evidence.** Before any worker that failed is destroyed, in the debug pass and the full run, `vastai show instance <id> --raw` and `vastai logs <id> --tail 200` are saved to `vast-attempt-<n>-<why>.txt` in the run folder. Each call has a 30 s limit (`PAID_RUN_VAST_SECONDS`), and a failure or timeout never blocks the destroy. The Vast CLI is only called; its config, credential and state files are never read.
- **Second rental.** After a confirmed host drop only, the debug pass releases that worker and rents ONE more offer (a different one) inside the same cap, with its own `--max-hours`. It does so only if an offer's `$/hr x max_hours` fits the cap left; otherwise it stops and says so. There is never a third rental, and the full run never re-rents after a host drop. The summary lists each rental with its offer, instance id, status and spend, and the total against the cap. `--plan` describes up to 2 rentals of `--max-hours` each and the worst case above.
- **Empty debug markers.** After each release, paid_run runs `jobs/checkpoints.py abandon` for every `omnivoice_debug-*` unverified marker whose checkpoint folder is empty or missing, so a later plain `vi cloud down` does not refuse over them. A debug folder that holds anything, and every other stage's marker, are left alone.
- **Data.** `--debug-rows` (default 128) train rows are taken from the start of `omnivoice_data` by position only (`jobs/debug_slice.py`), plus 4 dev, 2 style and 8 replay rows. No labels are read and nothing is selected. The slice is built under home's cache and goes only to the rented worker, like the real run's data.
- **Listening set.** Stage 10's clips come from a 5-step checkpoint. They show that generation works end to end and say nothing about voice quality. They are for human listening only and are never scored.
- **Results.** These are `~/.local/state/vi/paid-run/<run-id>/debug-summary.txt` and `.json`, plus the worker's own summary in the stage output. The exit code is 0 only when every stage passed, and 16 otherwise. The same gates as a real run apply first: rehearsal (exit 15), base-model revision (exit 14), disk (exit 11) and data ids (exit 12).
- **Rehearsal.** `jobs/rehearsal/run.sh debug-pass` runs stages 1 to 11 at home on the CPU stubs (no Vast, no GPU), including the real handshake, receiver, venv build and checkpoint verification.
- **Tests.** `jobs/test_debug_pass.py` uses a stub `vi` and never calls Vast.

### Status and stop

Agents can read a run's progress and ask it to stop safely. Neither command can change the cap, the hours limit, or the attempt count, and neither rents or retries anything.

```sh
python3 -I jobs/paid_run.py status --run-id omnivoice-ft-1 [--json] [--credit]
python3 -I jobs/paid_run.py stop --run-id omnivoice-ft-1 [--now]
```

- `status` reads the run's state file only and makes no `vi` call. `--credit` adds one `vi cloud status` call to show the account credit. Spend for the open attempt and the ETA are labelled estimates, and the ETA appears only after 3 step samples. An unknown run id exits 2 and changes nothing.
- The training step comes from the trainer output that `paid_run.py` already streams. It reads a tqdm bar (`150/5000 [02:10<...`) or a text line such as `Step 150/5000` or `step: 150 of 5000`. **Assumption:** the real trainer's line format has not been checked against a live run. If neither shape matches, `status` says "no step read yet" and `stop` releases the worker at once, so check `status` early in the first real run.
- `stop` writes `<run-id>.stop` beside the state file. It refuses (exit 2) if the run is not running. Before training starts (offer, up, preflight) it releases the worker immediately. During training it waits for the newest checkpoint (saved every 500 steps) to reach home and be acknowledged, for at most 10 minutes, then tears the worker down and exits 8. It also releases at once if no checkpoint is pending or the step is unreadable.
- `stop --now` skips the wait. It sends SIGTERM to the recorded `paid_run.py` pid, but only after checking that the process is this run's (command line holds `paid_run.py` and the run id, and the start time matches). Otherwise it signals nothing.
- A stop file left from an older run is deleted when a run starts, so it never stops a new run with the same id.

### Parallel checkpoint push, progress, and early host-drop stop

- The worker pushes each big checkpoint file (64 MiB or more) as up to `VI_PUSH_STREAMS` (default 4) byte-range chunks over concurrent rsync connections; home joins them only once `SHA256SUMS` has arrived. Only the `vi-publish` receiver module allows 4 connections (was 1); `vi-out` and `vi-checkpoint` stay at 1.
- **Speedup is unmeasured.** All four streams share the one reverse ssh tunnel. The probe's 6.84 MB/s (leg b of `jobs/push-probe.sh`) used four separate ssh connections, so it does not show what the tunnel gives. Stage 9's time limit therefore assumes no speedup (`VI_PUSH_SPEEDUP` default 1.0: 1.5 x bytes / the measured single-stream rate, at least 600 s, clipped by the rental deadline). In the next debug pass, compare the "received home" progress lines and the stage-9 seconds with the single-stream rate. Set `VI_PUSH_SPEEDUP` to the ratio you measure (at most the stream count) to shorten the limit.
- Stage 9 holds `push.lock` and `push.pid` for the length of its push, so the poller's `start_push_if_needed` does not launch a second push loop beside it. It also writes the byte total to `push.total`.
- While a push runs, `on-worker.sh` prints the bytes received home every `VI_PUSH_PROGRESS_SECONDS` (default 60), counted from the receive dir (`jobs/push_progress.py`). In a debug pass the line reads `debug-pass: stage 9 ckpt-push: still running (received home N MB of M MB (P%))`.
- Early host-drop stop: after `VI_EARLY_DROP_SECONDS` (default 75) of polls failing with "Connection refused", `on-worker.sh` runs `VI_GONE_CHECK_CMD` once per outage. `paid_run.py --debug-pass` sets it to `jobs/paidrun/vast_gone_check.py <instance id>`, which only reads (`vastai show instance`, `vastai logs`). If Vast says the instance is gone, the stage ends as the lost-worker give-up does; nothing new is rented. If it is still listed (or Vast cannot be read), waiting continues up to the usual limit (5 minutes in a debug pass). A refusal shorter than 75 s never asks Vast. `0` turns the early check off.
